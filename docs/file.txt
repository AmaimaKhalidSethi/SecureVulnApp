Core Architecture Concept
The entire app runs in one of two modes controlled by a single environment variable:
APP_MODE=vulnerable  →  all security OFF, attacks succeed
APP_MODE=secure      →  all security ON, attacks blocked
Every middleware, controller, and route reads req.appConfig (injected by modeMiddleware.js) to decide which code path to execute. Same codebase, same endpoints, completely different behavior. The mode can be changed at runtime via POST /api/mode/set without restarting the server — nodemon auto-restarts and picks up the new .env value.

Day-by-Day Vulnerability Implementation

Day 3 — Authentication
Vulnerable behaviors:

Passwords stored as plain text in MongoDB
Client sends role: "admin" in body → gets admin role
No input validation — single character passwords accepted
Wrong email returns "No account found with that email" (user enumeration)
No limit on login attempts

Secure behaviors:

bcrypt with 10 salt rounds
Role always forced to "user" server-side
express-validator: min 8 chars, uppercase + lowercase + number required
Generic "Invalid credentials" for all failures
Account locked for 15 minutes after 5 failed attempts

Key files: models/User.js, controllers/authController.js, middleware/authMiddleware.js, routes/auth.js
Auth bypass (vulnerable mode):

authMiddleware.js sets req.user = { id: 'bypass', role: 'admin' } when enforceJwt: false
Any request to protected route succeeds with no token

The attack:

// MongoDB query becomes:

passwordMatch = (password === user.password) || (typeof password === 'object');

### Day 5 — XSS

**Stored XSS attack path:**
```
CommentForm.jsx → POST /api/comments → commentController.js
→ vulnerable: storedContent = content (raw)
→ Comment.create({ content: "<script>alert()</script>" })
→ GET /api/comments returns raw content
→ CommentList.jsx: dangerouslySetInnerHTML → SCRIPT EXECUTES
```

**Reflected XSS attack path:**
```
SearchPage.jsx → GET /api/comments/search?q=<script>...
→ vulnerable: searchedFor: rawQuery (not encoded)
→ SearchPage.jsx: dangerouslySetInnerHTML → SCRIPT EXECUTES
```

**Secure defenses:**
- Backend: `DOMPurify.sanitize(content)` before `Comment.create()`
- Frontend: `{comment.content}` as text node instead of `dangerouslySetInnerHTML`
- Search: HTML entity encoding (`<` → `&lt;`, `>` → `&gt;` etc.)

**Comment model stores both:** `rawContent` and `sanitizedContent` for side-by-side comparison in UI

**Test payloads:**
```
<script>alert("XSS")</script>
<img src=x onerror="alert('XSS via img')">
<svg onload="alert('XSS via SVG')"></svg>
"><svg onload=alert(1)>

### Day 6 — CSRF

**How the attack works:**
- Browser auto-attaches cookies to cross-origin requests
- `evil.html` fires `fetch()` to `localhost:5000/api/user/transfer`
- In vulnerable mode: CORS is wide open, no token check → transfer executes
- Victim never interacted with the request

**Vulnerable mode:** `csrfMiddleware.js` calls `next()` immediately — no check at all

**Secure defense — Synchronizer Token Pattern:**
1. Frontend calls `GET /api/user/csrf-token` → receives UUID token
2. Token stored server-side in `Map` keyed by session ID
3. All POST/PUT/DELETE must include `X-CSRF-Token: <token>` header
4. Server compares submitted token vs stored token
5. evil.com cannot read your `/csrf-token` response (same-origin policy) → can't forge

**Additional defense:** Origin header checked against `http://localhost:3000`

**Key fix applied:** `evil.html` needed CORS fix in `server.js` to allow `file://` origin in vulnerable mode

**`csrfHelper.js`:** Axios interceptor auto-attaches token to all mutating requests

### Day 7 — IDOR

**The distinction:**
```
Authentication = valid JWT ✅
Authorization  = JWT belongs to THIS resource owner ❌ (missing in vulnerable mode)
Attack procedure:

GET /api/users → full user list with all MongoDB _id values exposed
Copy victim's _id
GET /api/users/<victim_id> with attacker's JWT → returns victim's profile
PUT /api/users/<victim_id> with { role: "admin" } → privilege escalation

Vulnerable code:
javascript// No ownership check — fetches any user
const user = await User.findById(req.params.id);
// Mass assignment — accepts any fields including role
await User.findByIdAndUpdate(targetId, { $set: req.body });
Secure code:
javascriptconst isOwner = (req, targetId) => req.user.id === targetId.toString();
if (!isOwner(req, targetId) && req.user.role !== 'admin') {
  return res.status(403).json({ error: 'Access denied' });
}
// Field whitelist — role cannot be updated by client
const allowedFields = ['username', 'email'];

**`securityLogger.js`** runs passively on every request — scans `req.body`, `req.query`, `req.params` for:
- MongoDB operator objects (`$gt`, `$ne`, `$where` etc.)
- XSS patterns (`<script>`, `onerror=`, `javascript:` etc.)
- Path traversal (`../`, `%2e%2e` etc.)
